operational domain (routes, fleet, recurring schedules, and the daily
Trip-generation job) now exists end-to-end, which Fares/Seating/Booking
(Phase 4+) will build directly on top of.

## Findings, ordered by severity

1. **[Fixed, real test-coverage gap] `PATCH /api/v1/vehicles/{id}/` (`vehicle-update`) had zero tests** — every sibling write endpoint in `network`/`fleet`/`scheduling` has both a happy-path-PATCH-is-audited test and a cross-client-404 test; `Vehicle`'s update view was the sole exception, found via a scripted `reverse()`-reference diff against all 15 named URLs. Fixed: added `test_vehicle_patch_updates_mutable_fields_and_is_audit_logged` and `test_cross_client_vehicle_patch_is_a_404_not_a_403` to `apps/fleet/tests/test_fleet.py`, mirroring `VehicleType`'s/`Driver`'s existing pattern exactly. 219/219 backend tests pass, ruff clean.
2. **[Fixed, real accessibility-coverage gap] `trips.spec.ts` had 3 interactive states never axe-checked**: the filtered-list state, the post-inline-assignment list state, and the cancel-dialog-with-a-reason-filled state — every other Phase 3 e2e spec file axe-checks every state it reaches, this was the one exception. Fixed: added an `AxeBuilder` assertion to each of the 3 states. All 7 `trips.spec.ts` tests still pass, all axe-clean including the newly-checked states.
3. **[Reported, not fixed — tenancy-adjacent, per §10.6.3] `apps/scheduling/services.py::_cancel_future_trips_for_schedule` reads via `Trip.all_objects.filter(...)` instead of the tenant-scoped `Trip.objects`.** Not a live vulnerability today — this function only runs inside `update_schedule()`, always in request context, filtered to a `schedule` object that was itself already tenant-verified by the view's own `Schedule.objects` queryset before reaching the service, so no cross-tenant row can actually surface through this path currently. It's a convention inconsistency worth tightening for defense-in-depth: if this function is ever called from a wider context in a future phase, the ORM-level tenancy filter would be silently bypassed with no RLS-equivalent second layer catching it inside a request (RLS itself still applies at the DB level regardless, but the codebase's own stated convention is "`all_objects` only for the documented Celery/system-bypass case"). Proposed fix: change `Trip.all_objects.filter(...)` to `Trip.objects.filter(...)` on line 123 — a one-line change, but touches tenancy-scoped code, so per self-check.md §10.6.3 this is reported rather than silently fixed.
4. **[Observation, not a defect, unchanged since Slice 3] 2 new `drf-spectacular` enum-naming-collision warnings** (`Status61dEnum` reused across `Trip.status` and another choice set, `StatusE94Enum` similarly) — schema still valid, drift-check still passes, same cosmetic class as the pre-existing `KycStatusEnum`/`BookingModeEnum` warnings Phase 1/2 already named.
5. **[Not a defect, confirmed pre-existing and unrelated] The 2 `profile-menu.spec.ts` failures** — same root cause Fleet's own self-check already diagnosed (accumulated e2e-test Businesses, now 114, pushing `Integra E2E KYB Review Business` past the `SelectedBusinessStore`'s `limit=100` fetch window). Re-confirmed via direct DB query this round. Still deliberately not fixed (would require either an arbitrary limit bump or a destructive DB reset, neither done without being asked).
6. **[Fixed during this session, before the formal self-check began] `NavShell`'s profile/business-switcher dropdown was `w-72` (288px) anchored `right-2` against a `w-64` (256px) sidebar — 32px wider than its own container, spilling the panel's left edge to `x: -41px`, off the browser viewport.** User-reported via screenshot, root-caused by direct `boundingBox()` measurement (`x: -41` before, `x: 8` after), fixed in `projects/layout/src/lib/nav-shell.ts` by anchoring `left-2` unconditionally instead of the collapsed-only/expanded-only conditional. Verified: `layout` library's 24 Karma tests pass, `profile-menu.spec.ts`/`nav-collapse.spec.ts` pass (except the pre-existing Finding #5 issue). Named here because it's a real Phase-3-adjacent UI fix (surfaced by Phase 3 adding 2 more nav items, pushing the trigger lower) even though it landed before this formal report was started.
7. **[Fixed, real, the visual loop's one blocker] Trips' 8-column table hid the Compliance and "Change status" columns entirely at every viewport, including 1440px (authoritative)** — live-measured (not just judged from a screenshot): no page-level horizontal scroll existed, but the table's own `overflow-x-auto` wrapper genuinely overflowed with the action button reachable only via undiscovered horizontal scroll. Fixed: constrained the Vehicle/Driver `<select>` cells (`max-w-40`) and made the Actions column `sticky right-0`, so "Change status" is always in-viewport and clickable regardless of scroll position — verified live via `boundingBox()` at all three viewports plus an end-to-end click with zero manual scrolling. Full detail, plus 4 more fixed defects and 1 caught false positive, in `docs/ui-review/3-network-scheduling-fleet/iteration-1.md`.
8. **[Fixed, real test-robustness gap, not a product bug] `trips.spec.ts`'s Escape-dismiss test failed reproducibly in isolation** — root cause: `Trip`'s `service_date`-ascending ordering combined with this file's own accumulated 52 trips (from many runs across this session) pushed a freshly created trip past page 1's 25-row window before the test's unfiltered row lookup ran. Fixed: every row-locating test in `trips.spec.ts` now scopes through the Route filter first (a `filterByRoute()` helper), which is also just how a real operator would find one specific trip in a long list. 7/7 pass reliably in isolation afterward.
9. **[Cleanup opportunity, not fixed — pre-existing, app-wide, not Phase-3-specific] Every business-scoped list screen's `syncBusinessFilter`/`syncFilterOptions` effect passes `{ allowSignalWrites: true }`, which Angular's own console warning says has been a no-op since this version** ("writes are always allowed"). Confirmed via a live console-listener sweep across all 7 Phase 3 screens (16 messages: 7 pre-existing/documented 404s from the local-dev `white-label/resolve/` gap, 9 of this same deprecation warning). Removing the option from all ~7 call sites app-wide would silence it with no behavior change, but it's cosmetic console noise, not a defect — not fixed this round, flagged for whenever another change touches those files.

## 3. The named 5%

- **The ad-hoc N+1 query-count check (`GET /trips/` at 10 queries flat) was not committed as a permanent regression test** — verified live for this report, but nothing stops a future refactor from silently reintroducing an N+1 on any Phase 3 list endpoint without a test catching it. Same gap class Phase 2's report named for `GET /clients/me/` before that phase added a permanent test for it.
- **No single Playwright test chains the full "create a Route with stops → create a Schedule against it → let the Celery job generate real Trips → assign a Vehicle/Driver → transition the Trip through its full lifecycle" flow end-to-end.** Every individual step has coverage; the full operational chain a real operator would follow does not, in one continuous test. Same class of honest gap Phase 1/2's own reports named for their own multi-step flows.
- **The Celery Beat generation job's actual scheduled firing (01:00 UTC daily) has never been observed running for real** — Slice 3's verification confirmed the periodic task is correctly registered and enabled, and `generate_trips()`/`generate_trips_for_schedule()` are unit-tested directly, but no test has let real wall-clock time pass and observed `celery-beat` actually trigger a run end-to-end against the live stack. A structural gap, not a suspected bug.
- **No dedicated full-keyboard-completion test exists for the Trip status-transition dialog** (radio group → conditional reason textarea → confirm button), unlike `kyc-queue.spec.ts`'s dedicated keyboard-only test for the KYC decide dialog. The Escape-dismiss/focus-restoration path is covered; the full tab-through-and-operate path is not.
- **The CI workflow has still never actually run** — same gap every prior phase's report has named, still true.
- **The repo still has zero git commits** — unchanged since Phase 0.
- **Date/time formatting is inconsistent across the module** (Schedule shows raw `07:30:00`/ISO dates; Trip shows `DatePipe`-formatted `9/15/26, 8:00 AM`) — found during the visual loop, judged cosmetic and not fixed. A real (if minor) polish gap.
- **The `businessNames()` lookup pattern (`Route`/`Stop`/`VehicleType`/`Vehicle`/`Driver`/`Schedule` list screens) silently falls back to a raw UUID when a Business isn't in the store's first-fetched page** — observed live on a Drivers screenshot this round, same root cause as the `profile-menu.spec.ts` Business-accumulation issue (Finding #5), not fixed for the same reason. Worth naming as a second, independent symptom of that one underlying test-data-volume condition, not a second bug.
- **The `allowSignalWrites: true` cleanup (Finding #9) is real cosmetic debt across ~7 files app-wide**, not fixed this round — a future pass touching any of those files should drop the now-inert option.
